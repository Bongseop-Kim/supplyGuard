## 0. 한 줄 목표와 요약

**목표(확정):**

> **계열사 보안 담당자가 스캔 결과를 판단·조치하는 업무를 AI 에이전트가 대신하도록,**
> ① 에이전트가 안전하고 재현 가능하게 진단을 수행하는 환경,
> ② 그 과정과 근거를 투명하게 보여주는 UI,
> ③ 영향도·우선순위·조치안을 판단 이력과 함께 축적·관리하는 시스템을 제공한다.

**만드는 것(수단):** 위 세 축을 갖춘 공급망 보안 전용 플랫폼(제안). ① 스캐너 격리 실행·타입 있는 워크플로우·재현 기록을 갖춘 실행 환경, ② 노드 캔버스·실행 뷰·근거 열람 UI, ③ 실행·판정·조치·예외 이력을 쌓아 재사용·추적·증빙하는 관리 시스템. AI 에이전트는 자연어 요청으로 파이프라인을 조립하고 판단 노드로 판정·조치안을 낸 뒤 사람 승인 후 실행한다. 효과는 KPI로 실측해 증명한다.

- **결과(먼저):** SBOM 생성·스캔은 기존 도구로 충분하다(플랫폼이 격리 실행으로 포함). 병목은 그 뒤다. 수천 건 중 진짜 위험을 고르고, 어느 계열사·서비스·담당자 일인지 찾고, 조치를 요청·추적·확인·증빙하는 일을 사람이 한다(가정). 플랫폼은 **"누가, 언제까지, 무엇을"**을 근거와 함께 내놓고 끝까지 추적한다(제안).
- **판단(AI):** 주인공은 스캐너 노드가 아니라 **판단 노드**(영향도 판정·우선순위·그룹 영향 열거·조치안)다. 스캐너는 기존 도구를 격리 실행할 뿐이다.
- **① 환경:** 노드 사이에 타입이 있는 보안 산출물(SBOM·Finding·Verdict·VEX 등)이 흐르고, 모든 실행은 도구 digest·DB 스냅샷·입력 해시와 함께 기록된다. 입력은 스캐너 무관(CycloneDX SBOM, SARIF, Grype/OSV JSON import 노드)이라 본선 현장 데이터가 무엇이든 받는다.
- **② UI:** 그래프·실행 과정·판정 근거(file:line, 출처, 스냅샷)를 그대로 보여 줘 사람이 검토·승인할 수 있게 한다.
- **③ 관리:** 판정은 일회성이 아니다. (서비스, 패키지@버전, 취약점) 단위 판정을 이력과 함께 쌓아 변경이 없으면 재사용하고, 조건이 바뀌면 재판정하며, 조치 기한·예외·증빙을 추적한다. 사내 판정 이력은 외부 모델에 없는 지식이 된다.
- **차별점(제안·해석):** 관리 도구(Dependency-Track·DefectDojo)는 결과를 모으고 상태를 기록하지만 판정은 사람이 한다. 체이닝 도구(n8n)는 연결은 하지만 보안 산출물·격리·근거 개념이 없다. 이 플랫폼의 차별점은 **AI 판단 + 근거 + 축적된 판정 이력**이다.

### 1.2 과제 원문과 해석

**과제6 원문(공식 확인):** "SW 공급망 스캐닝 에이전트 기획 — SBOM 생성 및 취약점 스캔 결과를 영향도·우선순위로 연결하는 아키텍처 설계 / AI 에이전트 기반의 자동 조치안 도출 및 보안 개선 워크플로우 기획".

해석(제안·해석):

- 대회 이름이 말하듯 목적은 실제 업무의 **AI 전환(AX)**이다. 새 스캐너나 새 기술을 만드는 과제가 아니다.
- 출발점은 스캔 **결과**다. 스캔은 이미 돌아간다고 전제하고, 그 결과를 "영향도·우선순위"와 "조치안·워크플로우"로 바꾸는 것이 과제다.
- 과제 유형은 **기획**(아키텍처 + 워크플로우)이다. 과제 문구의 "보안 개선 워크플로우"를 실제로 조립·실행·검증할 수 있는 플랫폼으로 구현해 기획을 증명한다. 본선은 현장 데이터로 1박 2일 안에 프로토타입을 만들게 하므로, 현장 요구를 노드 조합으로 빠르게 맞출 수 있는 구조가 유리하다.
- 대회 목적은 인재 발굴이다. 심사위원은 롯데 현업·AI 전문가·경영진과 OpenAI AI 전문가다(공식 확인).

### 2.2 현재 업무 흐름과 병목 6가지 — 가정

> 롯데 내부 업무 흐름은 **확인되지 않았다**. 아래는 업계 일반 사례와 공개 근거로 추정한 흐름이며 본선 현장 데이터로 검증해야 한다. 롯데이노베이트가 그룹 계열사 IT를 운영한다는 점(언론 보도·공식 사업 소개 기반 해석) 때문에 이 병목은 계열사 수만큼 곱해진다고 본다(추정).

```text
스캔 결과 수천 건 → ① 진짜 위험 선별 → ② 서비스·비즈니스 영향 파악 → ③ 담당자 찾기·조치 요청·조율
                  → ④ 패치 없음·브레이킹 시 대안 → ⑤ 조치 확인·감사/공시 증빙
신규 위협 발생 → ⑥ 그룹 전체 수작업 확인(①~⑤를 긴급 반복)
```

| # | 병목 | 왜 어려운가 |
| --- | --- | --- |
| ① | 수천 건 중 진짜 위험 선별 | 스캐너는 "취약 버전이 있다"만 말한다. 실제로 취약 코드를 호출하는지, 악용되고 있는지는 사람이 본다 |
| ② | 어느 계열사·서비스인지, 결제·개인정보 등 비즈니스 영향 | SBOM과 서비스 카탈로그·데이터 등급이 따로 있어 사람이 연결한다 |
| ③ | 담당자 찾기·조치 요청·조율 | 담당자 정보가 흩어져 있고, 요청마다 근거 설명을 다시 쓴다 |
| ④ | 패치 없음·브레이킹 업그레이드 시 대안 | 권고문의 완화책(설정·입력 차단)을 읽고 서비스에 맞게 번역해야 한다 |
| ⑤ | 조치 확인·감사/공시 증빙 | 재스캔 확인, "영향 없음" 판단의 근거 기록을 수작업으로 남긴다 |
| ⑥ | 신규 위협(Log4Shell, xz, Shai-Hulud, Trivy 침해) 시 그룹 전체 확인 | 버전 범위·시간 창·비밀 범위를 전 계열사 자산에 대해 빠짐없이 찾아야 한다 |

### 2.4 왜 기존 도구로 안 풀리는가 — 제안·해석

| 기존 도구 | 하는 일 | 멈추는 지점 |
| --- | --- | --- |
| 스캐너(Grype, OSV-Scanner, Trivy, SAST) | 취약 버전·코드 패턴 탐지, KEV·EPSS 기반 정렬 | 우리 코드가 실제로 취약 경로를 쓰는지 모름. 정렬 산식 비공개(Grype·Snyk, 공식 확인) |
| Dependabot·Renovate | 버전 업 PR | 단순 버전 업 PR은 65~75% 병합(학술)되지만, 패치 없음·브레이킹·완화책은 다루지 않음 |
| Dependency-Track·GUAC·DefectDojo | 자산·의존성 그래프, 결과 집계·중복 제거, 분석 상태·조치 상태 기록 | 열거·집계·기록은 하지만 판정·조치안 작성·담당자 조율은 사람 몫. 판정이 근거와 함께 쌓이지 않아 다음 스캔에 재사용·재판정 조건 관리가 안 됨 |
| 범용 워크플로우 도구(n8n 등) | 노드 연결, 스케줄, 외부 API·LLM 호출 | 보안 산출물 타입, 스캐너 격리 실행, 재현 기록, 판정 근거 개념이 없어 판단 로직과 통제를 사용자가 매번 직접 구현 |
| 범용 LLM 단독 | 설명·요약 | 업그레이드 권고의 27.76%가 존재하지 않는 버전(Sonatype, 벤더 주장), 위험 과대 예측(프리프린트) |

빈자리는 **판정과 번역**, 그것을 **재현·감사 가능하게 조립·실행하는 환경**, 그리고 **판정·조치를 이력으로 쌓아 다음 판단에 쓰는 관리 체계**다. 스캔 결과를 우리 코드·자산·담당자 맥락에서 판정하고, 실행 가능한 조치로 번역하고, 그 과정을 증빙으로 남기고, 조치 완료까지 추적하는 일이다.

## 3. 해결 방향

### 3.1 제품 형태 — 제안

**공급망 보안 전용 플랫폼**을 직접 만든다. 0절 목표의 세 축과 그 위에서 일하는 AI 에이전트로 구성한다.

| 축 | 구성 | 역할 |
| --- | --- | --- |
| ① 진단 환경 | 스캔 전용 실행 환경 | 타입 검사된 DAG를 실행. 스캐너는 digest 고정 격리 컨테이너, 판단 노드는 LLM + 지식 계층, 모든 실행을 재현 기록으로 남김 |
| ② 투명한 UI | 노드 캔버스·실행 뷰 | 입력→SBOM→스캔→보강→판단→조치→출력 노드를 연결·편집하고, 실행 결과를 노드별 산출물·근거로 열람 |
| ③ 축적·관리 | 결과 종합·관리 시스템 | 실행·자산·발견·판정·VEX·조치·예외·이벤트를 축적. 판정 재사용·재판정 큐, 조치 추적(기한·SLA), 사람 검토 큐, 예외 관리, 추이, 감사 증빙 export(4.10) |
| (에이전트) | AI 에이전트 | 자연어 요청 → 그래프 조립 → 캔버스에서 사람 확인·수정·승인 → 실행. 개별 노드를 도구로도 호출. 판정 시 축적된 사내 판정 이력을 참조 |
| (진입) | 트리거 | 정기 스캔(스케줄) / 신규 KEV·MAL 이벤트 / 재판정 큐 / 수동 |

예: "계열사 A의 npm 서비스 전부 스캔해서 KEV 해당 건만 담당자별로 정리" → 에이전트가 `자산 목록(계열사 A, npm) → Syft → Grype → KEV 보강 → 조건 분기(KEV) → 악용 가능성 → 우선순위 → 담당자 라우팅 → 티켓 초안` 그래프를 제안하고, 사람이 승인하면 실행한다.

### 3.2 범용 체이닝 도구와의 차이 — 제안·해석

| # | 차별점 | 내용 | 근거 |
| --- | --- | --- | --- |
| 1 | 타입이 있는 보안 산출물 | 노드 사이에 SBOM(CycloneDX)·Finding·Enriched finding·Verdict(근거 포함)·VEX statement·Action plan이 흐르고, 연결 시 타입 검사 | 제안 |

| 7 | 축적된 판정 이력 | 판정이 근거·주체·시점과 함께 쌓여 다음 스캔에서 재사용되고, 무효화 조건이 걸리면 재판정. 사내 판정 이력은 유사 사례 검색 지식이 됨(4.10). n8n은 실행 로그만, Dependency-Track·DefectDojo는 사람이 입력한 상태만 남김 | 제안·해석 |

## 4. 아키텍처 — 제안

> 롯데 내부 아키텍처가 아니라 우리가 제안하는 시스템이다.

### 4.1 전체 구조

```text
[② UI] 노드 캔버스(편집) · 실행 뷰(노드별 산출물·근거) · 관리 화면(현황·추적·검토 큐·예외·추이·증빙)
   ▲▼
[AI 에이전트] 파이프라인 작성기 · 노드 도구 실행기 · 사람 승인 게이트
   │ 워크플로우 정의(graph JSON, typed ports)
   ▼
[① 실행 엔진] 타입 검사 → DAG 러너 → 노드 실행(격리 컨테이너 / 결정론 / LLM) → 캐시 → 실행 기록
   │
   ▼
[노드 카탈로그] 입력 · SBOM · 스캔 · 보강 · [판단] · 조치 · 출력 · 제어
   │                                   ▲ 판정 재사용 조회 / 유사 사례 검색
   ▼                                   │
[③ 관리 계층] 축적 저장소(Run·Asset·Finding·Verdict·VEX·Action·Exception·Event) · 재판정 큐 · 조치 추적
   │
   ▼
[지식 계층] 정확 조회 · 취약 조건 카드 RAG · 에이전틱 코드 검색 · 자산 그래프 · 사내 판정 이력 RAG
가드레일(신뢰 등급·승인·권한·가명 처리)은 모든 계층에 걸친다.
```

진입: (A) 정기 스캔 스케줄, (B) 신규 위협 이벤트(KEV CVE ID별 전체 레코드 diff — 신규 등재 및 `knownRansomwareCampaignUse`·`notes`·`requiredAction`·`dueDate` 변경, OSV `MAL-` 신규 항목), (C) 재판정 큐(무효화된 판정, 4.10.2), (D) 수동·에이전트 요청. 진입 B는 그룹 영향 열거를 먼저 실행해 대상 자산을 확정한 뒤 판정·조치로 간다. 모든 실행 결과는 관리 계층에 기록되고, 판단 노드는 판정 전에 관리 계층에서 재사용 가능한 판정을 먼저 조회한다.

### 4.2 UI

- **노드 캔버스:** React Flow(xyflow) 계열 라이브러리로 노드 배치·연결·파라미터 편집. 포트 타입이 맞지 않는 연결은 그리는 순간 거부한다.
- **에이전트 제안 보기:** 에이전트가 만든 그래프를 기존 그래프와의 차이(추가·삭제 노드·엣지)로 보여 주고 승인·수정·거절을 받는다.
- **실행 뷰:** 노드별 상태·소요 시간·입출력 산출물. Verdict는 근거 file:line 코드 조각과 출처(KEV·OSV 레코드, 조회 시점)를 펼쳐 보이고, 실행 기록(digest·스냅샷)을 함께 표시한다. 재사용된 판정은 "재사용(원 판정 시점·주체)" 표시와 원 판정 링크를 단다.
- **관리 화면:** 실행을 넘어선 누적 현황(위험 현황·조치 추적·검토 큐·예외·추이·증빙)은 4.10.4에 정리한다.

### 4.3 워크플로우 정의 — 타입 있는 포트

그래프는 JSON으로 저장한다: `nodes[{id, type, version, params}]`, `edges[{from: node.port, to: node.port}]`, `trigger`. 노드 타입마다 입출력 포트 타입을 선언한다.

| 산출물 타입 | 내용 | 기반 형식 |
| --- | --- | --- |
| `SBOM` | 구성요소 목록(purl·버전·의존 관계) | CycloneDX |
| `Finding` | (purl, version, advisory ID, 위치, 탐지 도구) | 스캐너 출력 정규화 |
| `EnrichedFinding` | Finding + KEV·EPSS·CVSS·Vulnrichment·수정 버전·MAL, 레코드별 `source`·`fetched_at` | 제안 |
| `Verdict` | `{status, justification, condition, snippets[file:line], call_path[], 출처}` | CycloneDX analysis 상태에 대응 |
| `Priority` | 결정 트리 등급(Track/Track\*/Attend/Act)·기한 등급·결정 입력 스냅샷 | SSVC형 |
| `ImpactSet` | 영향 서비스·시스템·계열사·담당자·노출·데이터 등급 | 자산 그래프 |
| `ActionPlan` | 담당자별 무엇을·언제까지·근거, 후보 버전·완화책 | 제안 |
| `VEXStatement` | 판정 + 근거 | OpenVEX / CycloneDX VEX |

검증 규칙: 그래프는 비순환이어야 하고, 모든 필수 입력 포트가 연결돼야 하며, 출력 부작용 노드(티켓 발송·PR·메시지) 앞에는 승인 게이트가 있어야 한다. 저장·실행 전에 같은 검사기를 사람 편집과 에이전트 생성 양쪽에 적용한다.

### 4.4 실행 엔진

| 요소 | 설계 |
| --- | --- |
| DAG 러너 | 위상 정렬 실행, 독립 노드 병렬, 노드별 재시도·타임아웃, 실패 노드 이후만 재실행 |
| 실행 방식 | (1) 격리 컨테이너: Syft·Grype·OSV-Scanner·cdxgen·Trivy 등 외부 도구 (2) 결정론: 정규화·사실 조회·결정 트리·그래프 질의·타입 변환 (3) LLM: 판단 노드의 해석·근거 판정·문장 작성 |
| 샌드박스 | 이미지 digest 고정, 비root, 입력 읽기 전용 마운트, 네트워크는 허용 목록(패키지 레지스트리·취약점 DB·피드 미러)만, 비밀 미주입, CPU·메모리·시간 제한 |
| 캐시 | 키 = 노드 타입·버전 + 파라미터 + 입력 산출물 해시 + 스냅샷 ID. 같은 키면 재사용 |
| 실행 기록 | 실행 ID별로 그래프 버전, 노드별 도구 버전·digest, 취약점 DB 스냅샷(Grype DB 빌드 날짜 등), KEV·EPSS 스냅샷 날짜, 입력 커밋 SHA·lockfile 해시, LLM 모델·프롬프트 버전, 산출물 해시 |
| 재실행 | 실행 기록의 스냅샷으로 재실행하면 결정론·컨테이너 노드는 같은 산출물을 내야 한다(LLM 노드는 일치율을 측정) |

근거: Trivy 침해(CVE-2026-33634)는 보안 스캐너 자체가 공급망 공격 경로가 된 사례다. 인포스틸러가 CI 비밀을 노렸으므로 스캐너에 비밀을 주지 않고 digest로 고정하는 것이 직접 대응이다(공식 확인 + 제안). 2026-10 기준 후보 버전은 Syft v1.55.0, Grype v0.121.0, OSV-Scanner v2.7.0, Trivy v0.76.1, cdxgen v13.5.0이다(공식 확인).

### 4.5 노드 카탈로그

| 범주 | 노드 | 입력 → 출력 | 실행 방식 |
| --- | --- | --- | --- |
| 입력 | 저장소, 자산 목록, 스캔 결과 import(CycloneDX·SARIF·Grype·OSV JSON) | — → 저장소 참조·자산 목록·`SBOM`·`Finding` | 결정론 |
| SBOM 생성 | Syft, cdxgen | 저장소 → `SBOM` | 격리 컨테이너 |
| 스캔 | Grype, OSV-Scanner, Trivy(선택, digest 고정) | `SBOM` → `Finding` | 격리 컨테이너 |
| 보강 | KEV, EPSS, Vulnrichment, OSV/GHSA 조회, MAL | `Finding` → `EnrichedFinding` | 결정론(정확 조회) |
| **판단** | 악용 가능성, 우선순위, 그룹 영향 | `EnrichedFinding`(+저장소) → `Verdict`·`Priority`·`ImpactSet` | LLM + 지식 계층 + 결정론 검증 |
| 조치 | 조치안 생성, 담당자 라우팅 | `Verdict`·`Priority`·`ImpactSet` → `ActionPlan` | LLM(선택·설명) + 결정론 후보 |
| 출력 | VEX, 티켓, 메시지, PR 초안, 보고서 | `ActionPlan`·`Verdict` → 외부 산출물 | 결정론, 발송은 승인 후 |
| 제어 | 트리거(스케줄·KEV/MAL 이벤트), 조건 분기, 사람 승인 게이트 | 임의 | 결정론 |

스캐너 출력은 import 노드와 같은 정규화기를 거치므로 현장에서 다른 스캐너 결과를 받아도 판단 노드 이후는 그대로 쓴다. 여러 스캐너는 병렬로 돌려 합친다(단일 SCA 도구 의존은 비권장, 학술).

### 4.6 판단 노드 — 플랫폼의 주인공

#### 4.6.1 악용 가능성(영향도 판정) — 핵심 AI 역할

1. 조건 추출: 취약점별 **취약 조건 카드**(수정 커밋 diff, 변경 함수, 트리거 설정·입력, 공개 진입 API)를 정확 조회하고, 없으면 diff에서 LLM이 조건만 요약한다(라인 인용). 카드는 하이브리드(BM25+벡터) 색인.
2. 코드 근거: 색인 없이 **에이전틱 검색**(grep, LSP 참조, 호출 그래프, 파일 범위 읽기)으로 대상 코드에서 조건을 찾는다. 질의 대부분이 정확한 심볼이라 grep·LSP가 주력이다(학술·프리프린트 혼재 근거). 검색 도구는 샌드박스 안에서 읽기 전용으로 돈다.
3. 구조화 증거: `Evidence = {condition, snippets[file:line], call_path[], justification_code}`. 1~3단계는 도구를 호출하는 증거 수집 에이전트(OpenAI Responses API + function calling)가 맡는다.
4. 확률 판정: 수집한 증거를 입력으로 **OpenAI Decisions API**(`POST /v1/decisions`)에 `predicate` 질문을 던진다(예: "취약 함수가 도달 가능한가", "트리거 설정·입력 조건이 충족되는가"). 결과는 질문별 확률이다. Decisions API는 텍스트·JSON 입력에 타입 있는 답(predicate 확률·choice·score)을 돌려주고, 한 요청에 질문 최대 400개, GA, 모델은 `gpt-6-luna`만 지원한다(공식 확인, [OpenAI Decisions 가이드](https://developers.openai.com/api/docs/guides/decisions)). 자유 형식 근거 추출·도구 호출은 Decisions가 아니라 3단계에서 한다(문서 권고와 동일).
5. 비대칭 규칙 + 임계값: 기본은 affected. **증거 없는 "영향 없음" 금지.**
   - p ≥ 상한 → affected
   - p ≤ 하한 **그리고** (a) 심볼 부재·미import, (b) 과근사 호출 그래프에서 경로 없음, (c) 설정·입력 조건 미충족 중 하나가 file:line으로 증명됨 → not_affected
   - 그 외 → uncertain(사람 검토 큐)
   - 상한·하한은 노드 파라미터이며, 평가셋 라벨로 보정해 정한다(6.1). 문서도 "라벨 예시로 라우팅·검토 임계값을 정하라"고 권고한다(공식 확인).
6. 결정론 검증: 인용 라인 실존·심볼 포함, 호출 경로 엣지 재확인, 수치가 사실 조회 값과 일치하는지 대조. 검증 실패면 확률과 무관하게 uncertain으로 내린다.

대량 선별에도 같은 API를 쓴다. 스캔 결과 수천 건의 1차 분류(예: Mission·노출 등급 `choice`, "권고문에 workaround가 있는가" `predicate`)를 요청당 최대 400문항으로 묶는다. 다단계로 앞 답에 의존하는 판정은 요청을 나눈다(문서 권고).

근거: Vul-RAG(diff 기반 지식으로 정확도 16~24% 향상, 학술), CognixShield(F1 89%, 학술), VEX-Bench(이진 약 80% F1, 학술). 학술 연구에서 정확도를 올린 것은 CVE 설명문 RAG가 아니라 패치 지식 + 코드 검색 조합이다.

#### 4.6.2 우선순위 — SSVC형 결정 트리, 산식 공개

| 단계 | 입력 | 규칙 |
| --- | --- | --- |
| Exploitation | KEV, 랜섬웨어 플래그, EPSS 확률, PoC | KEV → active · EPSS ≥ 로컬 임계값(예: 0.1) 또는 PoC → poc · 그 외 none |
| Technical Impact | CVSS C/I/A, 유형 | 전부 High 또는 RCE·인증 우회 → total · 그 외 partial |
| Automatable | CVSS v4 AU, Vulnrichment | yes / no |
| Mission·노출 | 자산 그래프의 노출·데이터 등급(서비스 맥락) | minimal / support / essential |
| 악용 가능성 수정자 | 4.6.1 판정 결과 | not_affected면 한 단계 하향. **KEV는 Track\* 미만 금지** |
| 출력 | — | Track / Track\* / Attend / Act + 기한 등급 + 결정 입력 스냅샷 |

EPSS 0.1은 로컬 정책(FIRST 공식 임계값 없음, 공식 확인). 임계값은 노드 파라미터로 노출해 계열사별로 조정한다. BOD 22-01은 BOD 26-04로 대체(공식 확인)되었고, 26-04의 3/14/60일 등급은 Tenable 요약(벤더 주장), 원문 조합 표는 **미확인**이다. 심각도는 NVD → CNA → Vulnrichment ADP → GHSA/OSV → "미산정" 순 대체 조회하며, 미산정은 0점이 아니다. NVD 보강 축소 보도는 **미확인**(2차 보도).

#### 4.6.3 그룹 영향 열거 — 자산 그래프 고정 질의

- 데이터 모델: `Package(purl, version)` → `Artifact(digest/빌드)` → `Service` → `System` → `계열사`. 서비스에 `owner`, `oncall`, `internetExposed`, `dataClassification`(결제·개인정보), 중요도 등급. 신규 위협용으로 빌드 시각, CI 액션 참조(가변 태그·SHA), 러너 비밀 범위를 둔다.
- **고정 질의 템플릿**만 노드·도구로 노출한다: `blast_radius(purl, range)`, `workflows_using(action, mutable)`, `runs_between(t0, t1)`, `owners(service)`. 누락 하나가 실패이므로 벡터 top-k는 열거에 쓰지 않고, 자유 text-to-SQL보다 검증·인젝션 방어가 쉽다.
- 참고 구현: GUAC `query patch`/`query bad`, Dependency-Track, Backstage 카탈로그(공식 확인). 사내 연동 대상은 **미확인**.

#### 4.6.4 조치안 생성·담당자 라우팅

- 후보 버전은 OSV `fixed`·`osv-scanner fix`·레지스트리 API에서만 가져오고 실존·냉각 기간·MAL 검사. LLM은 후보 중 **선택**과 근거 인용만 한다(검증된 버전만 사용).
- 패치가 없거나 브레이킹이면 권고 workaround(설정 비활성화·입력 검증·경로 차단)를 런북·정책 RAG로 서비스별로 맞춘다.
- `ImpactSet`의 `owners`로 담당자별 `ActionPlan`(무엇을·언제까지·근거)을 묶는다.

#### 4.6.5 출력

- 담당자별 티켓·메시지(무엇을·언제까지·근거), 단순 버전 업은 PR 초안(빌드·테스트·재스캔 결과 첨부), OpenVEX/CycloneDX VEX, 보고서. 분석 상태는 Dependency-Track 체계를 따른다(공식 확인).
- 모든 출력에 실행 ID를 붙여 실행 기록(스냅샷·digest)으로 역추적할 수 있게 한다. 발송·PR 생성은 승인 게이트 뒤에서만.

### 4.7 AI 에이전트

| 역할 | 동작 | 통제 |
| --- | --- | --- |
| 파이프라인 작성기 | 자연어 요청 → 노드 카탈로그(타입·파라미터 스키마)만 사용해 graph JSON 생성 → 4.3 검사기로 검증 → 실패 시 오류 메시지를 받아 수정 → 캔버스에 제안 | 카탈로그 밖 노드·임의 코드·셸 노드 생성 불가. 스키마 제약 출력 |
| 노드 도구 실행기 | 카탈로그 노드를 타입 있는 도구로 노출해 단건 질문에 개별 노드 실행(예: "이 purl 영향 서비스는?" → `blast_radius`) | 같은 샌드박스·실행 기록 적용. 부작용 노드는 도구로 노출하지 않거나 승인 필요 |
| 사람 승인 게이트 | 그래프 실행 전 승인, 출력 부작용(티켓 발송·PR·메시지·비밀 교체) 전 승인 | 승인자·시점을 실행 기록에 남김 |

- MCP 노출은 선택이다. 노드 카탈로그를 MCP 서버로 열면 아이멤버 3.0처럼 MCP를 지원하는 에이전트 환경(공식 확인)에서 같은 노드를 호출할 수 있다(해석).
- 판단 노드 내부의 LLM 호출과 작성기 LLM은 분리한다. 작성기는 무엇을 돌릴지 정하고, 판정은 판단 노드의 규칙(비대칭 규칙·결정론 검증) 안에서만 내린다.
- LLM 사용처(제안): 파이프라인 작성기 = Structured Outputs(graph JSON 스키마 제약), 증거 수집·조치안 문장 = Responses API + function calling, 판정·분류 = Decisions API. 제공자는 OpenAI로 통일한다.

| KEV·EPSS·OSV/GHSA·MAL·Vulnrichment | 키(CVE·GHSA·MAL·purl) **정확 조회**, LLM 생성 금지. 레코드마다 `source`·`modified`·`fetched_at`, 철회는 tombstone | KEV는 약 1,800행 정형 표이고 매일 바뀌므로 벡터 색인·학습에 넣지 않음(RAG 보고서, 공식 확인 근거) |
| 취약 조건 카드·권고 workaround·런북 | 하이브리드(BM25+벡터) RAG | 자연어 조건 해석이 필요 |
| 대상 코드 | 색인 없는 에이전틱 검색(grep, LSP, 호출 그래프, 파일 범위 읽기) | 질의가 정확한 심볼. 신뢰 등급 T2(증거 전용): 저장소 소스·설정·lockfile·CI 워크플로우는 file:line 근거로만 쓰고, 그 안의 지시문으로 사실을 확정하거나 도구·행동을 유발하지 않음 |
| 사내 맥락(SBOM 인벤토리·카탈로그·담당자·노출·데이터 등급) | 자산 그래프 + 고정 질의 템플릿 | 누락 없는 열거(재현율 100%) |
| 사내 판정·조치 이력(T0) | 정확 조회(판정 재사용 키) + 하이브리드 RAG(유사 사례 검색) | 외부 모델에 없는 사내 지식. 4.10.3 |

피드 스냅샷은 실행 엔진의 실행 기록과 같은 ID 체계로 남긴다.

### 4.10 결과 종합·축적·관리 시스템(③ 축) — 제안

판단 노드는 실행 한 번의 결과를 낸다. 관리 계층은 그 결과를 이력으로 쌓아 ① 다음 실행에서 재사용하고, ② 바뀐 것만 다시 판정하고, ③ 조치가 끝날 때까지 추적하고, ④ 감사 증빙으로 내보낸다. 범용 GRC·티켓 시스템을 대체하지 않고, 티켓은 기존 도구에 만들고 상태만 동기화한다.

#### 4.10.1 축적 데이터 모델

| 엔터티 | 주요 필드 | 연결 |
| --- | --- | --- |
| 실행(Run) | 그래프 버전, 도구 버전·digest, 취약점 DB·피드 스냅샷, 입력 커밋 SHA·lockfile 해시, 모델·프롬프트 버전, 트리거 | 4.4 실행 기록과 동일 ID |
| 자산(Asset) | 서비스·시스템·계열사, 담당자·oncall, 인터넷 노출, 데이터 등급(결제·개인정보), 중요도 | 4.6.3 자산 그래프 |
| 발견(Finding) | (서비스, purl@version, 취약점 ID), 탐지 도구, 최초·최근 발견 Run, 상태(신규·지속·해소·재발) | Run, Asset |
| 판정(Verdict) | status·justification, 근거 file:line·호출 경로·출처, **판정 주체(AI/사람)**, 판정 시점, 판정 시 입력 해시·권고 `modified`·KEV/EPSS 값, 유효 여부 | Finding, Run |
| VEX 진술 | OpenVEX/CycloneDX VEX 문서, 발행 시점, 대응 판정 | Verdict |
| 조치(Action) | 담당자, 기한(우선순위 등급 기반), 상태(요청·진행·완료·검증됨·지연), 연결 티켓/PR, 검증 Run | Finding, Verdict |
| 예외·위험 수용(Exception) | 대상 Finding, 사유, 승인자, 승인 시점, **만료일** | Finding, Action |
| 이벤트(Event) | 신규 KEV/MAL 항목, 감지 시점, 영향 자산 목록, 대응 진행률 | Asset, Finding, Action |

저장소(제안): PostgreSQL 관계형 테이블에 위 엔터티를 두고, 자산 그래프는 같은 DB의 관계 테이블 + 고정 질의(뷰·재귀 CTE)로 표현한다. 별도 그래프 DB는 필요가 실측될 때만 검토한다. 판정·조치·예외는 덮어쓰지 않고 이력 행을 추가한다(감사 추적).

#### 4.10.2 판정 재사용 규칙

| 규칙 | 내용 |
| --- | --- |
| 재사용 키 | (서비스, 패키지@버전, 취약점 ID). 같은 키의 유효 판정이 있으면 판단 노드를 다시 돌리지 않고 재사용 |
| 무효화 조건 | (1) 해당 서비스의 코드·lockfile 해시 변경(판정 근거 파일 변경 포함) (2) 권고문 수정(OSV `modified` 갱신) (3) KEV 신규 등재 (4) EPSS가 로컬 임계값을 넘음 (5) 예외 만료 |
| 무효화 시 | 판정을 무효로 표시하고 **재판정 큐**에 넣음 → 판단 노드 재실행. 무효화 사유를 기록 |
| 사람 확정 판정 | AI가 덮어쓰지 못함. 무효화 조건이 걸리면 AI는 새 판정을 "제안"으로만 만들고 사람 검토 큐로 보냄 |
| 재사용 기록 | 재사용된 판정도 이번 Run에 "재사용(원 판정 ID)"으로 연결해 증빙 체인을 끊지 않음 |

근거 파일 변경 감지는 처음에는 lockfile·커밋 해시 단위(보수적)로 하고, 판정 근거 file:line 단위 세분화는 평가(6.4) 후 결정한다(제안).

#### 4.10.3 판정 이력을 지식으로

- 사내 판정·조치 이력(T0 신뢰 등급)을 RAG 대상으로 둔다. 새 판정 시 "같은 패키지·같은 취약 조건·유사 코드 패턴에 대해 다른 서비스·계열사는 어떻게 판정·조치했는가"를 검색해 판단 일관성과 설명 근거에 쓴다(제안).
- RAG 보고서의 결론은 "KEV를 학습시키는 건 의미 없다"였다. KEV는 공개·정형·매일 바뀌는 사실이라 정확 조회가 맞기 때문이다. 반면 사내 판정 이력은 **외부 모델이 가질 수 없는 내부 지식**(우리 코드에서 실제로 어떤 경로가 쓰이는지, 어떤 완화책이 통했는지, 어떤 예외가 승인됐는지)이므로 검색 대상으로 가치가 있다(해석).
- 통제: 검색된 과거 판정은 참고 근거일 뿐이다. not_affected는 여전히 이번 코드의 file:line 증거로만 확정한다(4.6.1 비대칭 규칙). 효과는 가설이며 6.5에서 평가가 필요하다.

#### 4.10.4 관리 화면

| 화면 | 내용 |
| --- | --- |
| 위험 현황 | 계열사·서비스별 열린 Finding을 우선순위 등급·데이터 등급·노출로 집계 |
| 조치 추적 | 담당자·기한·상태, 기한·SLA 준수 여부, 지연 건 목록·알림, 연결 티켓/PR 상태 |
| 사람 검토 큐 | uncertain 판정, 사람 확정 판정에 대한 AI 재판정 제안, 무효화 사유 표시 |
| 예외 관리 | 예외·위험 수용 목록, 승인자, 만료 임박 알림, 만료 시 재판정 큐 연결 |
| 추이 | 기간별 신규·해소·재발 건수, 반복 취약 패키지, 이벤트별 대응 소요 |
| 감사 증빙 export | 기간·계열사·서비스 범위로 VEX·판정 이력·실행 기록(digest·스냅샷)을 묶어 내보내기 |

각 항목에서 해당 판정의 실행 뷰(4.2)로 이동해 근거를 열람한다.

### 5.2 확산 시나리오 — 제안·해석

1. **한 계열사 정기 스캔**에 적용해 선별·조치 요청 시간을 측정. 반복 스캔이 쌓일수록 판정 재사용으로 사람 검토량이 줄어드는지 추적.
2. **그룹 공통 자산 그래프**로 확장: 신규 위협 시 전 계열사 영향 열거를 한 번에. 롯데이노베이트가 여러 계열사 IT를 운영한다는 구조상 효과가 곱해진다(해석).
3. **계열사별 워크플로우**: 계열사마다 다른 스캐너·정책 임계값·티켓 시스템을 노드 교체·파라미터로 맞추고, 새 요구는 자연어로 조립한다. 코드 수정 없이 확산하는 경로다(해석).
4. **외부 고객 보안 서비스**: 롯데이노베이트 보안 사업(컨설팅·구축·운영·관제, 이전 조사 기록)의 진단 후 조치 관리 상품으로 확장 가능(해석, 실제 사업 계획 **미확인**).
5. **사내 에이전트 연동**: 노드 카탈로그를 MCP로 노출하면 아이멤버류 사내 에이전트에서 호출 가능(해석, 내부 연동 방식 **미확인**).

## 6. 핵심 차별화 기능 5가지

| 기능 | 구현 방법 | 비즈니스 효과 |
|--------|--------|--------|
| SBOM 자동 생성 | Syft, CycloneDX | 오픈소스 자산 식별 |
| 위험도 우선순위화 | CVSS + KEV + EPSS + 서비스 맥락 | 조치 대상 선별 |
| 증거 기반 AI 분석 | LangGraph + 코드 분석 + RAG | 판단 근거 및 불확실성 제공 |
| 자동 패치 PR | GitHub API + 격리된 빌드·테스트 | 반복 수정 공수 절감 |
| 재검증 및 조치 관리 | CI + Grype 재스캔 + 감사 로그 | 조치 완료 확인 |

여기서 우선순위 모델을 단순히 LLM에게 맡기면 안 돼.

예를 들어 KEV에 등록되어 실제 악용 사례가 확인된 취약점은 정책 엔진이 우선 검토 대상으로 표시하고, LLM은 코드와 서비스 맥락을 분석해 추가 근거를 제공하도록 분리해야 해.

**가장 중요한 차별점은 자동 패치의 성공 여부를 말로 판단하지 않고, 실제 테스트와 재스캔 결과로 판정한다는 것**이야.
