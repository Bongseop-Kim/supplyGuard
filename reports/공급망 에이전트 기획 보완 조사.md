# 탐지보다 검증으로 승부하는 공급망 에이전트

작성 기준일: 2026-10-30 · 대상: LOTTE AX Challenge 2026 과제6(롯데이노베이트 "SW 공급망 스캐닝 에이전트 기획") · 보완 대상: `docs/LOTTE_SupplyGuard_AI.md` 4·5·7·8절

SupplyGuard AI의 기획은 방향이 맞다. 보완해야 할 것은 구체적인 수치와 규칙이다. 우선순위화는 CVSS·KEV·EPSS·도달성·서비스 맥락을 하나의 가중합으로 섞지 말아야 한다. **KEV가 모든 것을 덮어쓰고, EPSS가 나머지를 정렬하고, CVSS와 서비스 맥락이 긴급도 등급을 정하는 계층형 결정 트리(SSVC 방식)**로 설계하고, 공식을 공개해 감사 가능하게 만드는 것이 가장 방어하기 좋은 구조다. Grype와 Snyk 같은 상용·오픈소스 도구도 같은 방향으로 수렴하지만 공식은 공개하지 않는다. 자동 조치의 현실적 기준선은 두 가지로 나뉜다. 버전만 올리는 봇 PR은 **약 60~75%가 병합**된다. 반면 깨지는 업그레이드나 코드 수준 취약점에 대한 LLM 완전 자동 수정은 학술 벤치마크에서 **약 15~34%**에 그친다. 따라서 에이전트가 가치를 더하는 곳은 "단순 버전 업" 이후의 영역, 즉 충돌·호환성 파괴·전이 의존성·노이즈 감소다. 이 영역에서도 판정은 LLM 설명이 아니라 빌드·테스트·재스캔이 맡아야 한다. 데모 스택은 Syft → Grype(EPSS·KEV·risk 정렬 내장) → OSV-Scanner(교차 검증과 `osv-scanner fix` 기준선)로 하고, npm 생태계와 snyk-labs/nodejs-goof 포크를 쓰는 조합이 가장 재현성이 높다. Trivy는 2026년 3월 자체 공급망 침해 사고가 있었으므로 선택 도구로 두고 버전·digest를 고정한다. 평가는 "제안 유효 → 설치 → 빌드 → 테스트 → 재스캔 → 사람 수용"의 단계별 깔때기로 보고한다. 특히 **존재하지 않는 버전을 추천하는 환각률**(Sonatype 측정 GPT-5 기준 27.76%)을 결정론적으로 측정해 "도구 근거 유무" 비교 실험으로 제시하면, 정확도와 AI 이해도라는 심사 기준을 동시에 겨냥할 수 있다.

> 근거 수준 표기: **[공식 확인]** 표준·기관·도구 공식 문서를 이번 조사에서 직접 확인 · **[학술]** 학회·저널 논문 또는 arXiv 프리프린트 · **[벤더 주장]** 기업 보고서·마케팅으로 독립 검증되지 않음 · **[미확인]** 2차 출처나 사전 지식에 의존해 원문을 다시 확인하지 못함 · **[제안]** 근거를 바탕으로 한 우리의 설계 판단

## 네 신호는 서로 다른 질문에 답하므로 겹쳐 쌓아야 한다

각 신호의 의미부터 분리해야 한다. **[공식 확인]** CVSS v4.0 Base 점수는 심각도이지 위험이 아니다. 명세는 Threat·Environmental 지표로 보강해야 "더 포괄적인 위험 평가 입력"이 된다고 명시한다. 유일한 Threat 지표인 Exploit Maturity(E)가 정의되지 않으면 **최악값인 Attacked로 간주**하므로, Base 점수만 쓰면 구조적으로 과대평가된다 ([FIRST CVSS v4.0 Specification](https://www.first.org/cvss/v4-0/specification-document)). **[제안]** 따라서 KEV 등재 시 E=Attacked, 공개 PoC 존재 시 E=POC, 그 외 E=Unreported로 설정해 **CVSS-BT 점수를 명세에 맞게 산출**하면, 임의 가중치 없이 위협 정보를 CVSS에 녹일 수 있다.

**[공식 확인]** EPSS는 향후 30일 내 악용 활동이 관측될 **확률**(0~1)과 전체 대비 **백분위**를 함께 제공한다. FIRST는 확률을 주 값으로 보고하라고 권고한다(예: "15.3% (92nd)"). 구간 구분(binning)은 "주관적"이며 "보편적 정답이 없다"고 밝혀 **공식 임계값을 제공하지 않는다**. 같은 글은 전체 취약점 중 실제 악용되는 비율을 약 5%로 제시한다 ([FIRST EPSS binning](https://www.first.org/epss/articles/prob_percentile_bins)). **[벤더 주장]** EPSS v4(2025년 3월)를 소개한 글에 따르면 "CVSS ≥ 7" 정책은 전체 CVE의 50.7%를 처리하고도 커버리지 74.6%, 효율 약 6%에 그친다. 같은 커버리지에서 EPSS는 작업량 약 6%, 효율 47%를 보였다 ([Empirical Security](https://research.empiricalsecurity.com/research/introducing-epss-version-4)). 저자가 EPSS SIG 공동의장이자 상용 기업 소속이고 방법론이 상세하지 않으므로, 기획서에서는 "EPSS 측 보고"로 인용해야 한다.

KEV와 SSVC는 결정 구조를 제공한다. **[미확인]** KEV 등재 조건은 CVE ID, 신뢰할 수 있는 실제 악용 증거, 명확한 조치 방법이며 피드는 JSON으로 제공된다 ([CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)). 2025년 말 기준 약 1,484건, 그중 20.5%가 랜섬웨어 사용으로 표시됐다는 2차 집계가 있다 ([Cyble](https://cyble.com/blog/cisa-kev-2025-exploited-vulnerabilities-growth/)). 25만 건 이상의 CVE 가운데 1.5천 건 수준이므로 **KEV 미등재가 "악용되지 않음"의 증거는 아니다**. **[공식 확인]** CISA SSVC는 Exploitation, Technical Impact, Automatable, Mission Prevalence, Public Well-being Impact의 다섯 결정점으로 Track / Track\* / Attend / Act를 산출한다. 각 결과에 대한 일수는 제시하지 않는다 ([CISA SSVC](https://www.cisa.gov/stakeholder-specific-vulnerability-categorization-ssvc)).

조치 기한 규정도 바뀌었다. **[공식 확인]** CISA BOD 22-01 페이지에는 이 지침이 **폐지되어 BOD 26-04(2026-06-10)로 대체되었다**고 표시되어 있다 ([CISA BOD 22-01](https://www.cisa.gov/news-events/directives/bod-22-01-reducing-significant-risk-known-exploited-vulnerabilities)). **[벤더 주장]** Tenable 요약에 따르면 BOD 26-04는 외부 노출, KEV 등재, 자동화 가능성, 기술적 영향(전체/부분 통제)의 네 변수로 **3일(포렌식 분류 포함) / 3일 / 14일 / 60일 / 시스템 업그레이드 시 조치**라는 등급을 정한다 ([Tenable FAQ](https://www.tenable.com/blog/cisa-bod-26-04-FAQ-vulnerability-remediation-impact)). 원문 부록 A의 16개 조합 표는 직접 확인하지 못했다. 기존 기획서처럼 "KEV = 2주"를 현행 규칙으로 쓰면 낡은 정보가 된다. 오히려 **BOD 26-04의 네 변수가 SSVC 결정점과 거의 겹친다는 점**을 활용해 SLA 등급 산출의 근거로 삼는 편이 좋다.

### 도구들은 같은 구조로 수렴하지만 공식은 감춘다

**[공식 확인]** Grype는 EPSS를 "점수(백분위)"로 표시하고, KEV 주석과 0~100 범위의 RISK 열을 제공한다. 위협(EPSS, 단 **KEV면 최대 위협으로 EPSS를 덮어씀**), 영향(CVSS), 맥락(랜섬웨어 사용 가산)을 결합해 기본적으로 risk 순으로 정렬하지만, **산식은 공개하지 않는다** ([Anchore: Interpreting Grype results](https://oss.anchore.com/docs/guides/vulnerability/interpreting-results/)). **[공식 확인]** Snyk Risk Score(0~1000, Early Access)는 영향(CVSS C/I/A, 프로젝트 비즈니스 중요도)과 가능성(악용 성숙도, EPSS, CVE 연령, 패키지 인기 등)을 결합한다. **도달성은 가능성을 올리고 전이 깊이는 낮춘다.** EPSS 결측 시 기본값은 0.01055이며, 문서에 KEV 언급은 없다 ([Snyk Risk Score](https://docs.snyk.io/manage-risk/prioritize-issues-for-fixing/risk-score)). **[공식 확인]** OWASP Dependency-Track은 EXPLOITABLE / IN_TRIAGE / FALSE_POSITIVE / NOT_AFFECTED / NOT_SET 분석 상태와 변경자·시각 감사 이력을 제공하고, EPSS와 CycloneDX VEX를 지원한다 ([DT Analysis States](https://docs.dependencytrack.org/triage/analysis-states/), [DT docs](https://docs.dependencytrack.org/)). **[제안]** Grype의 구조(KEV 우선, CVSS 영향, 랜섬웨어 가산)와 Snyk의 맥락 수정자(도달성, 전이 깊이, 비즈니스 중요도)를 결합하되 **산식을 공개**하면, 두 도구가 불투명한 지점에서 분명한 차별점이 생긴다.

### 도달성은 우선순위를 낮출 뿐 자동으로 닫으면 안 된다

**[학술]** 약 300만 개 Maven 패키지를 분석한 연구에서 의존성 내 취약 코드까지 호출 경로가 닿는 패키지는 **1% 미만**이었다. 반면 전이 의존성까지 포함하면 약 1/3이 "취약"으로 표시됐다 ([Mir et al., arXiv 2301.07972](https://arxiv.org/abs/2301.07972)). **[벤더 주장]** Endor Labs는 함수 수준에서 90.5%가 도달 불가하며 SCA 노이즈를 92%(최대 97%) 줄인다고 주장한다 ([Endor Labs](https://www.endorlabs.com/use-case/sca-with-reachability)). 학술 결과와 방향은 같지만 고객 데이터 기반의 최선 사례 수치다. **[공식 확인]** Go의 govulncheck는 실제로 취약 함수를 전이 호출하는 경우만 보고하며, 심볼 단위 데이터를 검수한 Go vuln DB에 의존한다 ([Go Vulnerability Management](https://go.dev/doc/security/vuln/)). **[미확인]** 정적 호출 그래프는 리플렉션, 동적 디스패치, 설정 기반 경로를 놓쳐 거짓 음성을 만든다 ([Dietrich et al., ACM SCORED 2024](https://dl.acm.org/doi/pdf/10.1145/3689944.3696165)). 도구별 거짓 음성률을 독립적으로 비교한 벤치마크는 찾지 못했다. Log4Shell처럼 설정·리플렉션 경로로 악용되는 사례를 생각하면 결론은 분명하다. 도달성은 **reachable / unreachable / unknown 3상태**로 기록하고, unknown은 reachable로 취급하며, **KEV 항목은 도달 불가여도 Track\* 아래로 내리지 않는다** **[제안]**.

### NVD 공백 때문에 CVSS 단독 의존은 이제 불가능하다

**[미확인]** 여러 2차 보도에 따르면 NIST는 2026-04-15부터 모든 CVE를 보강하지 않고 KEV, 연방정부 사용 소프트웨어, EO 14028 핵심 소프트웨어 위주로 위험 기반 보강을 한다. 2026-03-01 이전의 미보강 CVE 약 29,000건은 "Not Scheduled"로 분류되고, NIST 자체 CVSS 부여도 중단해 CNA 점수에 의존한다 ([Help Net Security](https://www.helpnetsecurity.com/2026/04/16/nist-national-vulnerability-database-nvd-enrichment/), [The Hacker News](https://thehackernews.com/2026/04/nist-limits-cve-enrichment-after-263.html)). NIST 원문 공지는 직접 열람하지 못했다. **[공식 확인]** EPSS v4도 NVD 보강이 불안정해지자 cve.org의 CNA/ADP 데이터를 보조 출처로 추가했다 ([Empirical Security](https://research.empiricalsecurity.com/research/introducing-epss-version-4)). **[제안]** 심각도는 NVD → CNA 점수 → CISA Vulnrichment ADP → GHSA/OSV 심각도 → "미산정" 순으로 대체 조회한다. **미산정을 0점으로 처리하지 말고** "중간 + EPSS"로 다룬다. EPSS 이력이 없는 신규 CVE는 일정 기간 뒤 재평가하는 규칙을 둔다.

이상을 종합한 우선순위 결정 함수는 다음과 같다. 각 단계는 입력값과 함께 기록되어 재현할 수 있어야 한다.

| 단계 | 입력 | 판정 규칙 **[제안]** |
|---|---|---|
| 1. Exploitation | KEV, 랜섬웨어 플래그, EPSS 확률, 공개 PoC | KEV → active · EPSS ≥ 로컬 임계값(예: 0.1, 약 88백분위) 또는 PoC → poc · 그 외 none |
| 2. Technical Impact | CVSS C/I/A, 취약점 유형 | C/I/A 모두 High 또는 RCE·인증 우회 → total · 그 외 partial |
| 3. Automatable | CVSS v4 AU, Vulnrichment, AV:N/PR:N/UI:N | yes / no |
| 4. Mission·노출 | SBOM↔서비스 매핑, 인터넷 노출, 데이터 등급 | minimal / support / essential |
| 5. Reachability 수정자 | 호출 그래프 결과 + VEX 근거 | unreachable이면 한 단계 하향하되 KEV는 Track\* 미만 금지 |
| 출력 | — | Track / Track\* / Attend / Act + BOD 26-04 대응 기한 등급 + 결정 입력 스냅샷 |

EPSS 임계값 0.1은 FIRST가 제공한 기준이 아니라 우리가 정한 로컬 정책이다. 따라서 **확률, 모델 버전, 날짜를 함께 저장**해야 한다(백분위는 시간이 지나면 이동한다). "도달 불가로 하향" 같은 결정도 VEX로 남기되, **도달성만으로 우선순위를 낮춘 항목은 `not_affected`가 아니라 `under_investigation`으로 유지**하고 Grype VEX 필터 대상에서 제외한다(위 "자동으로 닫으면 안 된다" 원칙과 KEV Track\* 최소 등급 규칙 유지). `not_affected`는 호출 경로 없음, 취약 심볼 부재, 실행 조건 미충족이 **검증된 경우에만** 쓴다. **[공식 확인]** OpenVEX v0.2.0은 `not_affected`에 다섯 가지 justification(`vulnerable_code_not_in_execute_path` 등) 또는 impact_statement를 요구한다 ([OpenVEX spec](https://github.com/openvex/spec/blob/main/OPENVEX-SPEC.md)). Grype는 OpenVEX로 결과를 필터링할 수 있다 ([anchore/grype](https://github.com/anchore/grype)). **[미확인]** CycloneDX 분석 필드(state, `code_not_reachable` 등 justification, response)는 DT와 바로 호환된다 ([CycloneDX VEX](https://cyclonedx.org/capabilities/vex/)). **[제안]** 내부 표준 모델은 CycloneDX analysis로 두고, Grype 필터용 OpenVEX에는 검증된 `not_affected`만 내보낸다.

## 봇 PR은 3분의 2가 병합되고 LLM 완전 자동 수정은 3분의 1을 넘기 어렵다

결정론적 버전 업 봇의 실적은 생각보다 좋다. **[학술]** 2,904개 JavaScript 프로젝트의 Dependabot 보안 PR 15,243건 중 **65.42%가 병합**되었고 상당수가 하루 안에 병합됐다. 수동 분석한 미병합 사유는 주로 개발자가 같은 의존성을 직접 갱신한 경우였다. **빌드가 깨진 경우는 3.2%**에 불과했다 ([Alfadel et al., MSR 2021](https://realiselab.github.io/publications/On-the-Use-of-Dependabot-Security-Pull-Requests.pdf)). **[학술]** He et al.(IEEE TSE 2023)은 74.53% 병합률을 보고했다. 그러나 Dependabot의 호환성 점수가 너무 희소해 개발자의 의심을 해소하지 못했고, 알림을 줄이도록 설정하는 경우가 많았으며, **11.3%의 프로젝트는 Dependabot을 중단**했다. 저자들은 이상적인 봇의 조건으로 설정 가능성, 자율성, **투명성**, 자기 적응성을 제시한다 ([arXiv 2206.07230](https://arxiv.org/abs/2206.07230v3)). 결국 봇이 실패하는 이유는 빌드 파손보다 **노이즈와 근거 부족**이다. 에이전트가 PR마다 변경 로그 차이, 테스트 결과, 재스캔 결과를 첨부해야 하는 직접적인 근거가 여기에 있다.

semver를 믿으면 안 되는 이유도 데이터로 확인된다. **[학술]** Maven Central 업그레이드 119,879건 중 83.4%가 semver를 준수했고, 깨지는 변경이 실제로 영향을 준 클라이언트는 7.9%였다 ([Ochoa et al., arXiv 2110.07889](https://arxiv.org/pdf/2110.07889)). **[학술]** 재현 가능한 깨지는 업데이트 571건으로 구성된 BUMP 벤치마크에서 가장 흔한 유형은 **컴파일 실패(43%)**였다 ([arXiv 2401.09906](https://arxiv.org/pdf/2401.09906), [Byam](https://arxiv.org/html/2505.07522v3)). 패치나 마이너 업이라도 반드시 빌드와 테스트로 검증해야 한다.

LLM 수정의 실측치는 이보다 훨씬 낮다. **[학술]** Byam은 BUMP 컴파일 실패 103건에서 o3-mini가 **빌드 전체 수정 27%, 개별 컴파일 오류 수정 78%**를 기록했다고 보고한다. 실패 유형은 새 버전에 존재하지 않는 API 호출, 미해결 심볼과 새로 생긴 오류, 컴파일은 되지만 테스트 실패 등이었다. Qwen2.5-32B는 고친 만큼 새 오류를 만들어 순 개선의 중앙값이 0%였다 ([arXiv 2505.07522](https://arxiv.org/html/2505.07522v3)). **[학술]** SEC-bench(NeurIPS 2025)에서 최고 에이전트의 취약점 패치 성공률은 **34.0%**였다 ([arXiv 2506.11791](https://arxiv.org/pdf/2506.11791)). Vul4J 계열 연구에서는 Codex가 약 20.4%를 기록했다 ([Wu et al., ISSTA 2023](https://arxiv.org/abs/2305.18607v1)). **[벤더 주장]** Google의 Gemini 파이프라인은 sanitizer 버그의 **15%**를 수정했고 모든 수정을 사람이 검토했다 ([Google Research](https://research.google/pubs/pub52980/)). 벤더 수치는 측정 기준 자체가 다르다. Snyk는 ">80% fix accuracy"를 주장하고 ([Snyk docs](https://docs.snyk.io/scan-fix-and-prevent/scan-with-snyk/snyk-code/manage-code-vulnerabilities/fix-code-vulnerabilities-automatically)), Copilot Autofix는 커밋까지 걸리는 시간을 중앙값 28분 대 1.5시간으로 제시하지만 이는 **정확성이 아니라 속도**다 ([GitHub blog](https://github.blog/news-insights/product-news/secure-code-more-than-three-times-faster-with-copilot-autofix/)). 기획서의 기대 성공률을 정할 때 이 수치들을 기준선으로 쓰면 안 된다.

| 범주 | 수치 | 근거 수준 |
|---|---|---|
| Dependabot 보안 PR 병합률 | 65.42% (빌드 파손 3.2%) | 학술 |
| Dependabot PR 병합률(버전+보안) | 74.53% | 학술 |
| LLM 깨지는 업데이트 수리(빌드 전체) | 27% (o3-mini), 33.3% (BigBag) | 학술(프리프린트) |
| LLM 에이전트 취약점 패치 | 34.0% (SEC-bench) | 학술 |
| 산업 파이프라인 sanitizer 버그 수정 | 15% (Google) | 벤더 주장 |
| 상용 "fix accuracy" | >80% (Snyk) | 벤더 주장 |
| LLM 업그레이드 권고 중 존재하지 않는 버전 | 27.76% (GPT-5, 약 37,000건) | 벤더 주장 |
| LLM 추천 패키지 중 존재하지 않는 이름 | 상용 ≥5.2%, 오픈소스 21.7% | 학술 |

마지막 두 행이 에이전트 설계에 가장 직접적인 영향을 준다. **[벤더 주장]** Sonatype 2026 보고서는 GPT-5의 업그레이드 권고 약 37,000건 중 **27.76%가 환각**이었고, 존재하지 않는 버전 10,000건 이상과 실제 악성 패키지 추천 사례가 있었다고 밝혔다 ([SD Times](https://sdtimes.com/security/report-ai-hallucinates-27-of-upgrade-recommendations-for-open-source-projects/)). **[학술]** USENIX Security 2025 연구는 16개 LLM에서 추천 패키지의 19.7%가 존재하지 않았다고 보고했다. 환각된 이름이 반복 질의에서도 재현되어 "slopsquatting" 공격이 가능하다 ([USENIX](https://www.usenix.org/conference/usenixsecurity25/presentation/spracklen)). 반복률은 출처에 따라 43%와 58%로 다르게 인용되므로 원문 확인이 필요하다. 결론적으로 **LLM이 버전 번호를 만들어내게 해서는 안 된다**. 후보 버전은 OSV `fixed` 이벤트, 레지스트리 API, `osv-scanner fix`에서만 가져온다. LLM은 그 후보 중 선택하거나, 깨지는 변경에 맞춘 코드 수정을 제안하거나, 설명을 쓰는 역할로 제한한다 **[제안]**.

### 안전한 워크플로우는 업계 전체가 같은 형태로 수렴했다

Google, DeepMind CodeMender, OpenAI Aardvark 모두 **격리 생성 → 빌드·테스트 → 재현/재스캔 → 사람 검토 PR**을 따르며, AI가 작성한 보안 패치를 기본으로 자동 병합하는 주요 벤더는 없다 ([DeepMind](https://deepmind.google/blog/introducing-codemender-an-ai-agent-for-code-security/), [OpenAI](https://openai.com/index/introducing-aardvark)). **[공식 확인]** Renovate는 브랜치가 최신이고 검사가 통과한 경우에만 자동 병합한다. 다만 필수 상태 검사를 지정하지 않으면 "GitHub가 실패한 테스트가 있는 PR을 자동 병합할 수 있다"고 경고한다. `minimumReleaseAge`로 신규 릴리스에 냉각 기간을 두고(npm 게시 취소 가능 기간 때문에 3일 권장), `prCreation=approval`로 사람 승인 게이트를 둘 수 있다 ([Renovate config options](https://docs.renovatebot.com/configuration-options/)).

에이전트 자체도 공격 표면이다. **[벤더 주장]** Invariant Labs는 공개 저장소 이슈에 심은 지시문으로 GitHub MCP 에이전트가 비공개 저장소 데이터를 공개 PR로 유출하는 시나리오를 시연했다. 서버 패치로는 막을 수 없고, **저장소 단위로 제한된 토큰** 같은 아키텍처 통제가 필요하다는 것이 결론이다 ([Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability)). **[미확인]** OWASP Top 10 for Agentic Applications(2025-12)는 ASI01 Agent Goal Hijack, ASI02 Tool Misuse를 다룬다. 공식 원문은 확인하지 못했고 2차 요약에 의존했다 ([Teleport 요약](https://goteleport.com/blog/owasp-top-10-agentic-applications)). 권고문, README, 변경 로그, 이슈 본문은 모두 공격자가 통제할 수 있는 입력이다. 검증 빌드에서 npm `postinstall`을 실행하는 것도 그 자체로 공급망 위험이다.

**[제안]** SupplyGuard의 조치 파이프라인은 다음 순서로 고정한다. ① 스캔 결과에서 후보 버전을 결정론적으로 산출한다(OSV fixed / `osv-scanner fix`). ② 레지스트리 존재 여부, 냉각 기간, 악성(MAL-) 여부를 검사한다. ③ 네트워크는 레지스트리만 허용하고 비밀정보가 없는 임시 컨테이너에서 `npm ci --ignore-scripts`, 빌드, 테스트를 실행한다. ④ 재스캔으로 대상 CVE가 사라졌는지와 신규 권고가 없는지 확인한다. ⑤ 실패하면 LLM이 깨지는 변경에 맞춘 코드 수정을 제한된 횟수만 재시도한다. ⑥ 증빙을 첨부한 PR을 만들고 사람이 승인한다. 분석용 토큰은 읽기 전용으로 저장소 범위에 한정하고, PR 생성용 쓰기 권한은 별도 ID로 분리한다. CI 설정, 빌드 스크립트, 레지스트리 출처를 바꾸는 변경은 항상 사람 승인 대상으로 둔다. 기존 기획서의 "자동 병합 없음" 원칙은 근거상 타당하므로 그대로 유지한다. Renovate식 등급형 자동 병합(패치 레벨, 테스트 통과, API 변경 없음)은 "향후 정책 옵션"으로만 언급한다.

## Syft·Grype를 주축으로, OSV-Scanner를 기준선으로, Trivy는 고정해서 쓴다

**[공식 확인]** 후보 도구는 모두 Apache-2.0이고 2026년 10월에 릴리스가 있었다. 버전은 Syft v1.55.0, Grype v0.121.0, OSV-Scanner v2.7.0, Trivy v0.76.1, cdxgen v13.5.0, Dependency-Track 5.2.1이다 ([syft](https://github.com/anchore/syft/releases), [grype](https://github.com/anchore/grype/releases), [osv-scanner](https://github.com/google/osv-scanner/releases), [trivy](https://github.com/aquasecurity/trivy/releases), [cdxgen](https://github.com/CycloneDX/cdxgen/releases), [dependency-track](https://github.com/DependencyTrack/dependency-track/releases)). 역할 분담은 명확하다.

| 도구 | 강점 | 주의점 | SupplyGuard 역할 **[제안]** |
|---|---|---|---|
| Syft | CycloneDX·SPDX 출력, 이미지·디렉터리·아카이브, in-toto 증명 | 출력 포맷 버전 상세 미확인 | SBOM 생성(주) |
| Grype | EPSS·KEV·RISK 내장, `--sort-by risk`, OpenVEX, `sbom:` 입력 | 산식 비공개, DB가 120시간 넘게 지나면 스캔 거부 | 스캔·기준 순위(주) |
| OSV-Scanner v2 | osv.dev 데이터, `fix` 내장(npm·Maven), 오프라인 DB | EPSS/KEV 미제공, `fix`는 실험 기능 | 교차 검증 + 비 LLM 수정 기준선 |
| Trivy | 다중 권고 출처, VEX 허브 | 2026년 3월 공급망 침해, EPSS/KEV 미확인 | 선택적 2차 의견(버전·digest 고정) |
| cdxgen | CycloneDX 1.7, 도달성·증거(`evinse`) | npm 설치에 Node ≥24 필요, Homebrew 버전 지연 | P2 도달성 실험용 |
| Dependency-Track | 분석 상태·감사·VEX·정책 | 서버형이라 무거움 | 연동 대상으로만 언급 |

**[공식 확인]** Grype의 데이터 출처는 GHSA, NVD, CISA KEV, EPSS, 각 배포판 피드다. 설정에서 `max-allowed-built-age: 120h` 때문에 5일 넘은 DB로는 스캔하지 않는다 ([Grype configuration](https://oss.anchore.com/docs/reference/grype/configuration/)). 데모 재현성을 위해 **DB 스냅샷 고정 절차**가 필요하다. EPSS·KEV·risk의 JSON 키 경로는 문서에 없으므로 `grype -o json` 결과를 직접 확인해야 한다(**[미확인]**). **[공식 확인]** `osv-scanner fix`는 npm(package.json·lockfile)과 Maven만 지원하고, in-place / relax / override 전략과 안정된 `--format=json` 출력을 제공한다. 그러나 실험 기능이고, npm `overrides`와 git·경로 의존성을 무시하며, 재설치는 하지 않는다. 패키지 매니저 스크립트를 실행할 수 있다는 경고도 있다 ([Guided remediation](https://google.github.io/osv-scanner/experimental/guided-remediation/)). `fix`가 처리하지 못하는 `overrides`와 깊은 전이 의존성이 바로 LLM이 가치를 더할 수 있는 빈틈이다.

단일 스캐너를 믿으면 안 된다는 근거는 탄탄하다. **[학술]** 9개 SCA 도구를 비교한 연구는 취약점 수가 크게 달랐고 DB 품질이 핵심 차이였다며 단일 도구 의존을 권하지 않는다 ([Imtiaz et al., ESEM 2021](https://arxiv.org/abs/2108.12078)). **[학술]** 7개 SBOM 기반 스캐너를 정답이 정해진 SBOM 16개로 시험한 연구에서는 여러 도구가 **유효한 SBOM 입력에서 조용히 실패**했다 ([Rosso et al., arXiv 2512.17710](https://arxiv.org/abs/2512.17710)). **[학술]** 10,000개 저장소에서 GitHub SBOM, Syft, Trivy, Microsoft SBOM Tool을 비교한 연구는 도구 간 취약점 수가 대부분의 언어에서 크게 갈린다고 보고한다 ([arXiv 2607.04614](https://arxiv.org/abs/2607.04614)). 세부 수치는 검색 요약에서만 확인했다. **[제안]** 이 결과를 설계에 반영한다. 입력은 항상 lockfile로 하고, Grype와 OSV-Scanner 결과의 합집합·교집합·불일치를 함께 보여준다. "SBOM 구성요소 수 ≈ lockfile 패키지 수"를 확인하는 정합성 검사도 둔다.

**[공식 확인]** Trivy는 2026년 3월 GHSA-69fq-xp46-6x23 / CVE-2026-33634(Critical)에서 악성 v0.69.4 릴리스, trivy-action 77개 태그 중 76개 하이재킹(인포스틸러), 악성 Docker Hub 이미지 v0.69.5·v0.69.6이 확인됐다. 공식 Homebrew 포뮬러와 digest로 받은 이미지는 영향이 없었다 ([GHSA-69fq-xp46-6x23](https://github.com/aquasecurity/trivy/security/advisories/GHSA-69fq-xp46-6x23)). "보안 스캐너 자체가 공급망 공격 경로가 되었다"는 이 사례는 발표 서사에 좋은 소재다. 동시에 **에이전트가 실행마다 도구 버전과 체크섬을 보고서에 남겨야 하는 이유**가 된다.

### 데모 생태계는 npm, 저장소는 nodejs-goof 포크와 자체 픽스처

**[제안]** npm을 고른다. npm은 모든 도구가 읽는 결정론적 lockfile이 있고, Maven과 함께 `osv-scanner fix`를 지원하는 유일한 생태계이며, `npm ci && npm test`로 업그레이드-테스트 반복이 단순하다. Python은 자동 수정 기준선이 없다. 또 한 연구는 Python SBOM 생성기 출력으로는 스캐너가 취약점의 약 20% 이상을 찾지 못한다고 보고했다 ([arXiv 2409.06390](https://arxiv.org/abs/2409.06390)). pygoat은 lockfile과 테스트 없이 `requirements.txt` 고정만 있다 ([pygoat](https://github.com/adeyosemanputra/pygoat/blob/master/requirements.txt)).

| 저장소 | 라이선스 | lockfile | 테스트 | 판단 **[제안]** |
|---|---|---|---|---|
| [snyk-labs/nodejs-goof](https://github.com/snyk-labs/nodejs-goof) | Apache-2.0 | 있음 | `tests/`(단, `npm test`=`snyk test`이므로 교체 필요) | 1순위 "실제" 데모 |
| [OWASP/NodeGoat](https://github.com/OWASP/NodeGoat) | Apache-2.0 | 있음 | grunt, Cypress | 차선(2024 이후 갱신 없음, MongoDB 필요) |
| [appsecco/dvna](https://github.com/appsecco/dvna) | MIT | 없음 | 없음 | 제외(네이티브 모듈 포함) |
| [juice-shop](https://github.com/juice-shop/juice-shop) | MIT | 루트에 없음 | 풍부 | 제외(약 322MB, 앱 수준 취약점 중심) |

nodejs-goof에는 lodash 4.17.4, marked 0.3.5, moment 2.15.1 등 오래된 고정 버전이 있다. **lodash 4.17.4 → 4.17.21(안전한 패치 업)**과 **marked 0.3.5 → 4.x(깨지는 메이저 업)**가 자연스럽게 대비된다. 실제 테스트 스위트(supertest 기반 라우트 스모크 테스트와 lodash·marked·moment 동작 단위 테스트)를 추가해야 "업그레이드로 테스트가 깨지는" 시나리오가 의미를 갖는다. 별도로 약 10개의 취약 npm 패키지와 jest 테스트로 구성한 **자체 픽스처 저장소**를 만들어 CI 회귀용으로 쓴다. 이 저장소는 통제가 쉽고 라이선스 문제도 없다 **[제안]**. 실행 환경의 Node는 22이므로 cdxgen npm 설치는 불가능하며, 오래된 네이티브 모듈은 Docker로 격리한다.

## 성공률은 하나의 숫자가 아니라 여섯 단계의 깔때기로 보고한다

수정 벤치마크들은 모두 실행 기반의 단계형 판정을 쓴다. **[학술]** SWE-bench는 패치 적용 후 FAIL_TO_PASS가 통과하고 PASS_TO_PASS(회귀)가 유지되어야 "resolved"로 판정한다 ([SWE-bench README](https://huggingface.co/datasets/princeton-nlp/SWE-bench/blob/refs%2Fpr%2F2/README.md?code=true)). **[벤더 주장]** Meta AutoPatchBench는 빌드, 원래 크래시 미재현, 확장 퍼징 통과, 참조 패치와의 차분 테스트를 단계별 비율로 보고한다 ([CyberSecEval docs](https://meta-llama.github.io/PurpleLlama/CyberSecEval/docs/benchmarks/autopatch)). **[학술]** SEC-bench는 컴파일, PoC 미재현, 신규 이슈 없음을 성공 조건으로 두고, 인스턴스당 비용($0.87)도 보고한다 ([arXiv 2506.11791](https://arxiv.org/pdf/2506.11791)). **[제안]** 의존성 조치 에이전트에 맞춘 깔때기는 다음과 같다.

| 단계 | 판정 | 실패 유형 태그 |
|---|---|---|
| 1. 유효 제안 | 버전이 레지스트리에 존재하고 OSV `fixed` 이상이며 다른 영향 범위 밖, 악성·yanked 아님 | 환각 버전/패키지, 불충분한 수정 |
| 2. 설치 | lockfile 해석과 `npm ci` 성공 | 해석 불가, peer 충돌 |
| 3. 빌드 | 빌드·컴파일 성공 | 컴파일 실패, 존재하지 않는 API |
| 4. 회귀 | 기존 테스트 통과(PASS_TO_PASS) | 테스트 회귀 |
| 5. 재스캔 | 대상 권고 소멸, 신규 권고 없음(Grype+OSV) | 취약점 잔존, 신규 취약점 |
| 6. 사람 수용 | 검토자가 병합 가능 판정 | 과도한 변경, 설명 불충분 |

기존 기획서의 "패치 성공률 = 빌드·테스트·재스캔 모두 통과" 정의는 3~5단계에 해당한다. 앞뒤에 1단계(유효 제안)와 6단계(사람 수용)를 추가하고 각 단계를 N 대비 비율로 보고하면 된다. 결과는 버전 업만으로 해결되는 쉬운 사례와 BUMP식 깨지는 업데이트 사례로 **층화**해서 보고해야 한다. 쉬운 사례의 높은 성공률이 어려운 사례의 낮은 성공률을 가리지 않게 하기 위해서다. 외부 기준선(SEC-bench 34%, Google 15%)은 C/C++ 소스 패치이므로 의존성 조치와 직접 비교할 수 없다는 점도 명시한다.

### 우선순위와 근거 품질은 결정론적 검사로 먼저 거른다

**[제안]** 우선순위화 평가는 세 지표를 함께 보고한다. 첫째, OSV 기반 정답 대비 (패키지, 버전, 권고) 단위 탐지 정밀도·재현율이다. **[학술]** OSV를 버전 단위 정답셋으로 재구성하는 재현 도구가 있다 ([Mandl et al., arXiv 2604.21111](https://arxiv.org/abs/2604.21111)). 둘째, **알림 감소율** = 1 − (Act/Attend 건수 / 원시 탐지 건수)다. 셋째, 알림 감소율과 반드시 함께 보고할 **핵심 위험 재현율**(KEV 등재·고 EPSS 항목 중 상위 등급으로 분류된 비율)이다. 노이즈를 줄였다는 주장이 실제 위험을 빠뜨린 대가가 아니라는 것을 보여줘야 하기 때문이다. 여기에 BOD 26-04 네 변수 기반 기한 등급 배정의 정확도를 더한다. 감소율은 우리 데이터에서 실측하고, 공개 참고점(FIRST 약 5% 악용, Maven 도달 1% 미만, Endor 벤더 주장 92%)은 옆에 나란히 두기만 한다. **[벤더 주장]** Datadog은 런타임 맥락을 적용하자 CVSS critical의 18%만 critical로 남았다고 보고했다 ([Datadog](https://www.datadoghq.com/state-of-devsecops/)). 이 수치도 참고점으로만 쓴다.

근거 품질은 LLM 판정보다 **결정론적 이진 검사**를 우선한다. 검사 항목은 제안 버전의 레지스트리 존재 여부(Sonatype 27.76%와 직접 비교 가능한 "환각 버전률"), OSV 영향 범위 밖 여부, 신규 권고 유무, 인용한 CVE/GHSA ID의 실존과 패키지 일치, CVSS·KEV·EPSS 수치와 평가 시점 API 값의 일치다. 설명의 명확성·실행 가능성에만 LLM-as-judge를 쓴다. **[학술]** LLM 판정자는 위치·장황성·자기 선호 편향이 있으며 사람과의 일치도는 약 80%다 ([Zheng et al., arXiv 2306.05685](https://arxiv.org/abs/2306.05685)). 따라서 루브릭을 쓰고, 순서를 무작위화하며, 생성 모델과 다른 계열의 모델을 판정자로 두고, 사람이 라벨링한 약 30건과의 일치도(Cohen's kappa)를 보고한다. 가장 설득력 있는 실험은 **"LLM 단독" 대 "LLM + 도구 근거"의 비교(ablation)**다. 근거 계층이 환각 버전률과 조치 성공률을 얼마나 바꾸는지 보여주면 AI 이해도를 직접 입증할 수 있다.

### 신뢰성은 pass^k와 장애 주입으로 증명한다

**[학술]** τ-bench의 pass^k는 k회 독립 시행이 모두 성공할 확률로, 일관성을 측정한다. gpt-4o는 retail 도메인에서 pass^8이 25% 미만이었다 ([arXiv 2406.12045](https://arxiv.org/pdf/2406.12045)). **[학술]** ReliabilityBench는 입력 섭동과 도구·API 장애 주입까지 측정 범위를 넓혔다 ([arXiv 2601.06112](https://arxiv.org/pdf/2601.06112)). **[제안]** 운영 지표는 다음과 같다. 파이프라인 완주율(수정 정확성과 별개), pass@1과 pass^3, 재시도율, 단계별 타임아웃률, **멱등성**(이미 수정된 저장소를 재실행하면 신규 PR이 생기지 않음), 장애 주입(레지스트리 5xx, OSV 타임아웃, 잘못된 LLM JSON) 시 정상 저하율, p50/p95 지연, 사례당 토큰·비용, 구조화 출력 스키마 적합률이다. 업계 표준 목표치는 없으므로 임계값은 자체적으로 정하고 근거를 밝힌다.

평가셋 규모는 일정에 맞춘다. 연구 노트의 권장안은 약 10개 저장소 × 3~5개 CVE = 30~50건이며, 직접/전이, 패치·마이너/메이저, KEV/비KEV, 도달/비도달, **수정 버전 없음 2~3건**(에이전트가 지어내지 않고 "없음"을 말해야 함), 악성 패키지 2~3건으로 층화한다. **[제안]** 11월 4일 제출을 전제하면 P0는 npm 단일 생태계에서 nodejs-goof와 자체 픽스처로 **15~20건**을 만들고, 그중 5건 이상을 블라인드 평가용으로 떼어 둔다. 다중 생태계 30~50건은 본선 전 확장 목표로 둔다. 사례마다 저장소 커밋 SHA, lockfile 해시, 권고 ID, 정답 최소 수정 버전, 기대 우선순위 등급, 테스트 명령, 컨테이너 digest, OSV/KEV/EPSS 스냅샷 날짜를 기록한다. 이는 BUMP의 Docker 패키징과 SEC-bench의 격리 검증 관행을 축소해 적용한 것이다 ([BUMP](https://github.com/chains-project/bump)).

## 결론

이번 조사로 SupplyGuard의 경쟁 지점이 더 분명해졌다. 우선순위 신호(KEV, EPSS, 도달성)는 이미 Grype와 Snyk가 제품에 넣었으므로, "신호를 결합한다"는 것 자체로는 차별화가 되지 않는다. 차별화는 **공개된 결정 규칙, 재현 가능한 결정 스냅샷, 그리고 LLM을 생성자가 아니라 검증된 후보 사이의 선택자·설명자로 묶어 두는 설계**에서 나온다. 업계 수치가 이를 뒷받침한다. 버전 업 봇은 이미 3분의 2를 해결하고, 남은 영역에서 LLM은 3분의 1 남짓만 해결하며, 제약 없는 LLM은 4건 중 1건 이상 존재하지 않는 버전을 추천한다. 따라서 이 과제에서 "AI 에이전트"의 가치는 수정 성공률을 높게 부풀려 보여주는 데 있지 않다. 실패를 단계별로 잡아내고, 근거 계층이 환각을 얼마나 줄이는지 실측으로 보여주는 데 있다.

남은 불확실성은 구현 첫날에 해소할 수 있는 것들이다. Grype JSON 키 경로, 우리 데이터에서의 실제 알림 감소율, nodejs-goof의 기존 테스트 상태가 그렇다. 2026년에 바뀐 외부 조건(NVD 보강 축소, BOD 26-04, Trivy 침해)은 오히려 기획서를 최신으로 보이게 하는 소재다. 다만 NVD와 BOD 26-04 세부 내용은 원문을 확인하기 전까지 "미확인/벤더 요약"으로 표기해 두어야 한다.
